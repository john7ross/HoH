## Как запустить проект

Чекаут — это только исходники, собирать ничего не нужно. HoH написан на одной
стандартной библиотеке Python, файл [`requirements.lock`](requirements.lock)
намеренно пуст, так что подойдёт любой Python 3.11 или новее с `tkinter`.

```bash
python -m venv .venv          # по желанию; ставить туда всё равно нечего
PYTHONPATH=src python -m llm_harness doctor --project-root .
PYTHONPATH=src python -m llm_harness gui
```

На Windows и POSIX то же самое делают лаунчеры, без переменной окружения:

```bash
scripts/hoh.sh doctor --project-root .
scripts/hoh-gui.sh
```

`doctor` — первая команда, которую стоит запустить, и первая, которую стоит
прочитать. Он сообщает, что настроено, чего не хватает, и печатает по одному
конкретному следующему шагу на каждую находку. На свежем чекауте предупреждения
ожидаемы: Supervisor и Verifier по умолчанию — офлайновые заглушки, а Worker по
умолчанию — тестовый драйвер.

Установленные пакеты несут собственный интерпретатор в `runtime/python`; у
чекаута такого каталога нет, и лаунчеры используют системный `python3`.
Переменная `HOH_PYTHON` перекрывает оба варианта.

## Тесты

Один набор, только стандартная библиотека, без плагинов:

```bash
PYTHONPATH=src python -m unittest discover -s tests
```

Он идёт около минуты на Linux и около трёх на Windows. Всё остальное, что
проверяет релизный гейт, — тоже обычные команды:

```bash
PYTHONPATH=src python -m compileall -q src tests
PYTHONPATH=src python -m llm_harness protocol-conformance --distribution-root . --json
PYTHONPATH=src python -m llm_harness audit --project-root . \
  --check "python -m unittest discover -s tests" \
  --check "python -m compileall -q src tests" \
  --markdown
```

Аудит — тот самый гейт, который релиз обязан пройти. Он отказывается работать на
грязном дереве, блокирует незакрытые маркеры и выполняет переданные ему
проверочные команды. Эти команды проходят через ту же политику, что и команды
планирующей модели: **без оболочки**. Проверка вида `set X=Y&& python -m unittest`
будет отклонена — без оболочки она молча выполнилась бы как один мёртвый аргумент
программы `set`.

### Каким должен быть тест в этом проекте

- **Проверяйте поведение, а не текст исходника.** Тест, который грепает скрипт на
  подстроку, не доказывает, что команда внутри вообще запускается. Ровно такой
  тест месяцами проходил, пока релизная сборка под Windows была неработоспособна.
- **Убедитесь, что тест умеет падать.** Написав тест на исправление, верните баг
  и посмотрите, как тест упадёт. Тест, который проходит на сломанном коде, — не
  тест. Здесь это не пожелание: несколько исправлений в проекте закреплены
  тестами, единственным доказательством работоспособности которых и была такая
  мутационная проверка.
- **Не привязывайтесь к машине.** Тест, который спрашивает у настоящего `PATH`
  наличие программы, проходит или падает в зависимости от того, что на машине
  установлено. Подставляйте резолвер — образец в `tests/test_doctor.py`.
- **Плавающий тест — это дефект.** Найдите недетерминизм и закрепите его.
- **Никогда не ослабляйте проверку, чтобы тест прошёл.** Сначала решите, где
  ошибка — в продукте или в тесте, — и скажите, где именно.

## Стиль

Держитесь стиля файла, который правите. Комментарии объясняют *почему*, а не
*что*: почти весь странно выглядящий код здесь — исправление чего-то, что
действительно ломалось, и комментарий остался единственной записью об этом. Два
примера, которые стоит прочитать прежде, чем что-нибудь «упростить»: почему
`attempts.py` читает git в двоичном режиме и почему в `gui_widgets.py` ширина
карточки распространяется только в одну сторону.

## Архитектурные правила, которые не обсуждаются

Их держат тесты и протокол ревью, а не договорённость:

- **К git прикасается только Supervisor.** Worker выдаёт патч и никогда не
  коммитит, не мержит и не пушит. Critic изучает свидетельства и выносит решение;
  в репозиторий он тоже не пишет.
- **Гейт патча детерминирован и падает закрытым.** Каждый путь, которого касается
  патч, сверяется с `allowed_paths` до того, как что-либо применяется. Патч,
  который парсер не смог разобрать до конца, отклоняется, а не пропускается.
- **Каждая попытка работает в изолированном worktree.** Канонический чекаут
  никогда не является рабочим каталогом агента.
- **Журнал операций дописывается и переживает падение.** Любая операция, меняющая
  состояние, восстановима после убийства процесса в любой момент; маркеры
  `crash_point` существуют, чтобы тесты могли это доказать.

## Перед тем как открыть PR

1. Весь набор тестов зелёный, а `audit` не выдаёт ни одной находки.
2. Дефект исправлен везде, где применим его класс, а не только там, где его
   заметили. Если баг возник из-за чтения подпроцесса в текстовом режиме,
   проверьте остальные места, где читаются подпроцессы.
3. Строки, видимые пользователю, есть и на русском, и на английском.
   `validate_translations` роняет GUI, если ключа не хватает с одной из сторон.
4. Документация, которая упоминает изменённое, обновлена на **обоих** языках, и
   ссылки каждого языка ведут на файлы этого же языка.
5. Если изменилось что-то, что попадает в поставку, скажите об этом. Три пакета и
   их контрольные суммы пересобираются после последней правки, а не до неё — и
   сборка теперь отказывается работать на грязном дереве именно поэтому.

## Как сообщать об ошибках

Заведите issue на <https://github.com/john7ross/HoH/issues>: что делали, что
произошло и чего ожидали. Укажите платформу, работали вы в GUI или в CLI, и
приложите вывод `doctor` — он рассчитан на то, чтобы его вставляли в отчёт, и не
содержит секретов.

**По всему, что связано с безопасностью, issue не заводите** — см.
[SECURITY.ru.md](SECURITY.ru.md), где перечислено и то, что нельзя прикладывать
ни при каких обстоятельствах.
