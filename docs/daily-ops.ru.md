# Ежедневные операции

[English](daily-ops.md) · **Русский**

Этот рунбук описывает повседневное использование установленного приложения HoH на Windows, Linux и
macOS.

## Файлы

- `config.example.toml` — безопасный пример конфигурации без настоящих секретов.
- `harness.toml` — локальная операторская конфигурация, скопированная из `config.example.toml`.
- `scripts/hoh.ps1` — лаунчер на встроенном рантайме, используемый Windows Setup и инженерными
  проверками.
- `scripts/hoh.sh` / `scripts/hoh-gui.sh` — лаунчеры, вложенные в пакеты Linux и ресурсы macOS.
- `scripts/hoh-env.template.ps1` — шаблон переменных окружения с вырезанными примерами значений.
- `scripts/register-telegram-watch-task.ps1` — необязательная регистрация запланированного задания
  Windows для входящих команд Telegram.
- `scripts/register-workspace-scheduler-task.ps1` — запланированное задание Windows с минимальными
  привилегиями, выполняющее каждый подошедший по расписанию проект без наложения на активную
  блокировку исполнения проекта.
- `scripts/register-workspace-scheduler.sh` — эквивалентный пользовательский таймер systemd или
  LaunchAgent для macOS.
- `scripts/run-daily-ops.ps1` — цикл worker'а очереди с гейтом doctor для ежедневного исполнения.

## Первичная настройка

```powershell
.\scripts\hoh.ps1 init-project
```

Отредактируйте `harness.toml` под выбранный адаптер worker'а. Локальные эндпоинты моделей включаются
явно; оставьте пример секции `[[local_models]]` закомментированным, пока эндпоинт не запущен.
Отредактируйте `hoh-env.local.ps1` настоящими значениями окружения и держите его вне git.

`init-project` отказывается перезаписывать существующие локальные файлы. Используйте `--force` только
тогда, когда намеренно обновляете локальную конфигурацию из шаблонов.

Загрузите окружение в текущую оболочку:

```powershell
. .\hoh-env.local.ps1
```

## Настройка десктопа и разговор с Supervisor

Запустите **HoH** из меню приложений операционной системы. Из чекаута исходников эквивалентная
инженерная команда:

```powershell
.\scripts\hoh-gui.ps1
```

Используйте страницы в таком порядке:

1. **Роли** — выберите доступных Supervisor и Worker, при желании включите независимого Critic, затем
   сохраните трёхролевой профиль. Агенты, чей исполняемый файл или лаунчер не найден, не предлагаются.
   Устаревший или отредактированный вручную недоступный выбор отклоняется ещё раз до записи профиля.
2. **Настройки проекта** — настройте эндпоинты моделей Supervisor и verifier, пути рантайма,
   требование тестов, уровень доверия Worker, планировщик и безопасные одноразовые CLI-профили
   Worker. У каждого поля есть объяснение. Проверка окружения сообщает только имена переменных и то,
   определены ли они. Отсутствующий API-ключ можно вставить в маскированное поле сессии; он остаётся
   только в памяти до закрытия этого окна GUI и никогда не пишется на диск и в вывод.
3. **Агенты и подключения** — установите или обновите ACP-агента из Registry в каталог текущего
   пользователя `%LOCALAPPDATA%\HoH\agents`, изучите объявленные им методы входа, откройте вендорский
   процесс входа или настройте и проверьте удалённую Agent Card A2A v1. Значения секретов можно
   вводить только для текущего процесса, и в конфигурацию проекта они не пишутся.
4. **Политики MCP** — разбирайте Supervisor, Worker и Critic по отдельности. Держите планирующую и
   ревьюирующую роли на `reject`, пока им действительно не понадобится инструмент; для Worker
   выбирайте только нужные категории ACP и добавляйте серверы stdio/HTTP/SSE в области роли. Секреты
   вводите как `TARGET=SOURCE_ENV`, но никогда как значения.
5. **Чат с Supervisor** — опишите задачу и ответьте на уточняющие вопросы. HoH держит разговор в
   приватном каталоге состояния вне Git-репозитория проекта. Создание плана требует явного
   подтверждения, после чего обычным конвейером планирования Supervisor'а пишутся бриф, дорожная
   карта, файлы задач и записи очереди.
6. **Проекты** — зарегистрируйте несколько корней Git, изучите их общую сводку очереди только на
   чтение, настройте фоновые запуски с фиксированным интервалом и сводки Windows и Telegram, затем
   явно включите фоновый исполнитель уровня пользователя.
7. **Метрики** — изучите свидетельства вызовов, токенов, стоимости, длительности и качества; при
   необходимости добавьте точные ставки провайдера и модели, когда адаптер не сообщает стоимость.
8. **Операции** — запустите Doctor, изучите очередь вместе с историей прогонов и аудита, выполните
   одну задачу или всю очередь, повторите разобранную неудавшуюся задачу, восстановите подтверждённую
   прерванную задачу и запустите аудит.

Точные пути хранения показаны внутри **Настроек проекта**:

- настройки проекта: `<проект>/.hoh/harness.json`;
- профиль ролей: `<проект>/.hoh/role-profile.json`;
- чат с Supervisor: `<родитель-проекта>/.hoh-state/<проект>-<хеш>/supervisor-chat.json`;
- язык, тема и последний проект GUI: `%LOCALAPPDATA%\HoH\gui-settings.json` на Windows;
- значения секретов: только окружение Windows или процесса, запускающего HoH.

Повседневная работа над проектом не требует ни сырого JSON, ни терминала. Безопасная установка
стороннего ПО, вендорский вход и настройка удалённого подключения A2A доступны на странице **Агенты и
подключения**. Сборка релиза, точный откат, сверка, ручной обмен файлами ревью и экспорт журнала
остаются защищёнными инженерными и криминалистическими операциями CLI.

HoH устанавливает точно закреплённый пакет `npx`/`uv` в собственный каталог пользовательской области.
Прямые архивы из Registry принимаются только по HTTPS с опубликованной SHA-256 и ограниченной
безопасной распаковкой; записи без метаданных целостности остаются заблокированными на виду.
Аутентификация у провайдера может быть выполнена через ACP или известный вендорский CLI, тогда как
доступ к модели, политика организации и квота остаются проверками на стороне вендора. Любое
невыполненное предусловие блокирует отправку с видимой ошибкой.

## Несколько проектов и фоновые запуски

Страница **Проекты** на десктопе — обычная управляющая поверхность. Эквивалентные headless-команды:

```powershell
.\scripts\hoh.ps1 workspace register --project-root C:\work\first --json
.\scripts\hoh.ps1 workspace summary --json
.\scripts\hoh.ps1 workspace schedule --project-id <id> --enabled --interval-minutes 30 --notify-windows --json
.\scripts\hoh.ps1 workspace run-due --json
.\scripts\hoh.ps1 workspace service-install --interval-minutes 1 --json
.\scripts\hoh.ps1 workspace service-status --json
```

Реестр — `%LOCALAPPDATA%\HoH\workspace-v1.json`; он хранит пути проектов и политику расписания, но не
задачи и не учётные данные. Общая очередь вычисляется из существующего корня состояния каждого
проекта. Каждый подошедший по расписанию запуск вызывает `queue-run-loop`, поэтому обычные поведения
предполётной проверки ролей, аренды состояния, аренды исполнения Git, гейта Critic, аудита и
уведомлений остаются авторитетными. Отключите исполнитель ОС командой `workspace service-uninstall`;
удаление проекта из реестра никогда не удаляет его файлы и свидетельства очереди. Попытки доставки
уведомлений на рабочий стол записываются в `%LOCALAPPDATA%\HoH\desktop-notifications.jsonl`.

На установленном Linux используйте `hoh`; на macOS для headless-команд —
`/Applications/HoH.app/Contents/MacOS/HoH`. Состояние следует соглашениям ОС о пользовательских
данных, уведомления рабочего стола используют `notify-send` и `osascript`, а те же команды
`workspace service-*` устанавливают нативный пользовательский планировщик. Headless-работа по HTTP
описана в [`headless-server.ru.md`](headless-server.ru.md).

Изучите матрицу совместимости, подкреплённую свидетельствами:

```powershell
.\scripts\hoh.ps1 compatibility-matrix --project-root C:\path\to\repo --json
```

Матрица отвечает на один вопрос — что есть на этой машине:

- `available` — лаунчер или прямой эндпоинт присутствует и проходит предполётную проверку;
- `unavailable` — настроенная запись или запись Registry существует, но её лаунчера здесь нет.

Работает ли роль на самом деле — отдельный вопрос, и единственный способ ответить на него — запустить
её:

```powershell
.\scripts\hoh.ps1 role-conformance `
  --project-root C:\path\to\repo `
  --role worker `
  --json
```

Команда один раз прогоняет выбранную роль в одноразовом Git-репозитории и сообщает о каждой сделанной
проверке. Используйте `--agent`, `--model` или `--agent-version`, когда хотите, чтобы отчёт назвал
точную личность; без них личность сообщается как `unknown`, а прогон всё равно происходит. На диск
ничего не пишется: ответ описывает эту машину, эту версию агента и эту учётную запись в этот момент, а
сохранённый только устаревал бы, продолжая выглядеть авторитетным. Supervisor и Critic используют ту
же команду и проверяют контракты структурированного плана и решения плюс чистоту одноразового
репозитория.

Проверьте переносимый рантайм и настроенные интеграции:

```powershell
.\scripts\hoh.ps1 doctor --config .\harness.toml
```

## Предполётная проверка Worker'а и живой смоук

Именованные worker'ы провайдеров по умолчанию проходят предполётную проверку только на чтение:

```powershell
.\scripts\hoh.ps1 worker-smoke --config .\harness.toml --json
```

Она разрешает исполняемый файл, проверяет его версию, проверяет настройки безопасности, которыми
владеет провайдер, и не начинает хода агента. Добавьте `--live` явно, чтобы разрешить одно
изменение-кандидат в одноразовом репозитории:

```powershell
.\scripts\hoh.ps1 worker-smoke --config .\harness.toml --live --timeout 300 --json
```

Живой путь проверяет, что:

- адаптер worker'а можно построить;
- `[worker.capabilities]` соответствует реальному поведению изоляции;
- worker умеет выдать ожидаемый артефакт репозитория;
- проверка и коммит под управлением supervisor'а проходят успешно;
- канонический репозиторий соответствия остаётся чистым.

Для Hermes:

```powershell
.\scripts\hoh.ps1 hermes-check
.\scripts\hoh.ps1 worker-conformance --config .\harness.toml --timeout 300
```

Если Hermes просит вручную переключить модель или не может запустить ACP, остановите ежедневное
исполнение и почините конфигурацию Hermes до запуска задач из очереди.

Для Claude Code используйте `[worker] driver = "claude_code"`. Флаги разрешений и инструментов задаёт
HoH; не добавляйте в `args` флаги разрешений, инструментов, сессии, плагинов, MCP, Chrome, worktree и
фоновой работы. У именованного адаптера намеренно нет инструмента Bash, и сам он тесты не запускает.

Для OpenClaw используйте `[worker] driver = "openclaw"` и задайте явное значение `провайдер/модель`.
HoH использует `--local`, никогда не доставляет в канал и не переиспользует широкую конфигурацию
рабочего пространства и инструментов у оператора. Если `openclaw` не установлен, предполётная проверка
сообщает `available=false`, не пытаясь его установить и молча не откатываясь к другому Worker.

Codex и любой другой CLI могут выступать Worker'ом через обычный драйвер `command`, если его
неинтерактивный вызов читает stdin и правит текущий worktree. Интеграция остаётся во владении
оператора и не ослабляет профиль безопасности вложенных именованных драйверов.

Для Aider выберите запись каталога `aider` по умолчанию после того, как `aider --version` заработает в
той же среде Windows, из которой запускается HoH. Его декларативный профиль `process` отправляет
задачу через `--message-file`, принудительно добавляет
`--no-stream --yes --no-auto-commits --no-dirty-commits` и при необходимости передаёт выбранную модель
через `--model`. Учётные данные обязаны быть переменными окружения, а не аргументами CLI. Сначала
запустите `worker-smoke`, а затем явный живой `worker-conformance`, прежде чем поручать настоящую
работу из очереди.

Для другого одноразового coding-CLI создайте профиль на странице **Настройки проекта**: укажите его
исполняемый файл, транспорт промпта через stdin или файл, необязательные флаги файла промпта и модели
и по одному обязательному, запрещённому и базовому аргументу на строку. Сохранение выполняет ту же
проверку с отказом закрытым, что и загрузчик конфигурации; секретный флаг вроде `--api-key`,
конфликтующий флаг промпта или небезопасный запрещённый аргумент отклоняются.

У каждой попытки Worker'а теперь есть независимая проверка владения Git: если внешний CLI создаёт
коммит и сдвигает `HEAD`, HoH отклоняет завершение, даже если процесс вернул ноль. Канонический
репозиторий остаётся неизменным, а одноразовая попытка удаляется.

## Опрос команд Telegram

Для ручной непрерывной сессии опроса Telegram:

```powershell
.\scripts\hoh.ps1 telegram-watch --config .\harness.toml --iterations 0
```

Для ежедневного использования без присмотра зарегистрируйте задание ограниченного опроса:

```powershell
.\scripts\register-telegram-watch-task.ps1 `
  -Config .\harness.toml `
  -EveryMinutes 1 `
  -Iterations 1 `
  -RunNow
```

Удалите его так:

```powershell
.\scripts\register-telegram-watch-task.ps1 -Unregister
```

## Цикл исполнения очереди

Выполните работу из очереди настроенным worker'ом:

```powershell
.\scripts\run-daily-ops.ps1 `
  -Config .\harness.toml `
  -TimeoutSeconds 300 `
  -StaleMinutes 60
```

Скрипт сначала запускает `doctor`, если не передан `-SkipDoctor`. Затем он выполняет
`queue-run-loop`, пока очередь не опустеет, не будет достигнут `-MaxTasks` или блокер либо зависшая
задача не остановят исполнение.

Задайте постоянный предел подготовки worker'ов в конфигурации:

```toml
[scheduler]
max_parallel_tasks = 2
```

Ограниченные ожидания координации настраиваются отдельно от планирования:

```toml
[coordination]
state_lock_timeout_seconds = 5
execution_lock_timeout_seconds = 5
poll_interval_seconds = 0.05
```

Для разового операторского прогона вызовите лаунчер с `queue-run-loop --parallelism 2`. Пакет делят
только готовые по зависимостям задачи с непересекающимися `allowed_paths`. Отсутствие
`allowed_paths` означает монопольное исполнение. Каноническая проверка, коммиты, ревью Critic и
записи состояния остаются сериализованными. Если в пакете есть отказ, изучите каждый прогон в
возвращённом массиве `runs`: HoH даёт остальным уже начатым независимым worker'ам завершиться,
записывает все исходы и не начинает нового пакета.

Внешнему supervisor'у, которому нужен разбираемый результат, следует вызывать лаунчер напрямую с
`queue-run-loop --json`. Режим JSON возвращает один версионированный документ со всеми обработанными
прогонами и терминальным статусом (`empty`, `blocked`, `max_tasks_reached`, `review_blocked`,
`rollback_blocked`, `task_state_blocked`, `ready` или `audit_failed`). Все остальные команды `queue-*`
и `rollback-*` тоже принимают `--json`.

## Сквозной смоук процесса

Прежде чем менять ежедневный рунбук или делиться новым пакетом, запустите детерминированный смоук
управляемого процесса:

```powershell
.\scripts\hoh.ps1 workflow-smoke
.\scripts\hoh.ps1 workflow-smoke --mode blocker
```

`workflow-smoke` использует одноразовый git-репозиторий, спецификацию проекта, составленную
supervisor'ом, порождённые документы брифа и дорожной карты, поставленные в очередь JSON-файлы задач,
детерминированный обычный command-worker, проверки верификатора, коммиты под управлением supervisor'а,
свидетельства финального аудита и уведомитель-заглушку. Режим `blocker` намеренно роняет worker'а и
проверяет, что свидетельства уведомления о блокере создаются без секретов Telegram.

## Планирование нескольких задач

Задачи проекта могут добавить два необязательных поля:

```json
{
  "depends_on": ["foundation-task"],
  "priority": 20
}
```

`project-plan` рассматривает набор задач как направленный ациклический граф. Он отклоняет неизвестные
идентификаторы задач, дублирующиеся рёбра зависимостей и циклы до того, как что-либо поставит в
очередь. Отдельный `queue-add` принимает зависимости только тогда, когда эти идентификаторы задач уже
присутствуют в истории очереди.

На каждом последовательном шаге очереди HoH рассматривает только задачи, чьи зависимости дошли до
`done`. Среди готовых первым идёт наибольший целый приоритет; равные приоритеты сохраняют порядок
постановки. Используйте `queue-list --json`, `/queue` или `supervisor-status --json`, чтобы изучить
выбранную задачу и счётчики готовых и ожидающих. `dependency_blocked` означает, что работа в очереди
есть, но каждый кандидат ждёт зависимость не в состоянии `done`; это не значит, что очередь пуста.

## Передача внешнему верификатору

Проверьте переносимый вендоронезависимый протокол до подключения агента supervisor'а или верификатора:

```powershell
.\scripts\hoh.ps1 protocol-conformance --distribution-root . --json
```

После того как прогон очереди создал коммит, принадлежащий supervisor'у, возьмите идентификатор
прогона и экспортируйте его точные свидетельства ревью:

```powershell
.\scripts\hoh.ps1 queue-history --project-root C:\path\to\repo --json
.\scripts\hoh.ps1 review-export `
  --project-root C:\path\to\repo `
  --run-id <run-id> `
  --output C:\path\to\handoff\review-bundle.json `
  --json
```

Передайте `review-bundle.json` независимому агенту или сервису вместе с
`schemas/verifier-decision-v1.schema.json`. Верификатор обязан вернуть только документированный
объект решения. Полномочий на коммит и merge у него нет.

Импортируйте возвращённое свидетельство:

```powershell
.\scripts\hoh.ps1 review-import `
  --project-root C:\path\to\repo `
  --decision C:\path\to\handoff\verifier-decision.json `
  --json
```

Одобренное решение завершается успешно. Действительное отклонение записывается, но завершается
ненулевым кодом, чтобы автоматический цикл остановился. Отклонение само по себе никогда не меняет git;
Supervisor обязан определить работу по исправлению или явно применить политику промышленного отката.
Изучите все свидетельства так:

```powershell
.\scripts\hoh.ps1 review-list --project-root C:\path\to\repo --json
.\scripts\hoh.ps1 supervisor-status --project-root C:\path\to\repo --json
```

## Промышленный откат

Всегда сначала изучайте план:

```powershell
.\scripts\hoh.ps1 rollback-plan `
  --project-root C:\path\to\repo `
  --task-id task-001 `
  --json
```

Продолжайте, только когда `eligible=true`. Скопируйте возвращённый полный `target_commit` в точности и
задайте проверки, доказывающие желаемое состояние после отката:

```powershell
.\scripts\hoh.ps1 rollback-apply `
  --project-root C:\path\to\repo `
  --task-id task-001 `
  --expected-commit <полный-целевой-коммит> `
  --reason "Production regression" `
  --check "python -m unittest discover -s tests" `
  --json
```

HoH поддерживает несколько процессов CLI на одном корне состояния. Короткие обновления очереди,
журнала, ревью, аудита, операторских событий и смещения Telegram сериализуются арендой состояния.
Каноническое применение патча, коммит и откат сериализуются независимо арендой исполнения
репозитория. Поэтому одновременные команды либо завершаются по порядку, либо останавливаются после
заданного ограниченного ожидания с диагностикой владельца; живую блокировку они не удаляют никогда.

Изучите координацию до восстановления:

```powershell
.\scripts\hoh.ps1 lock-status `
  --project-root C:\path\to\repo `
  --json
```

`available=false` означает подтверждённого ОС живого владельца; дождитесь его или изучите указанные
PID, хост, команду, действие и метку времени. `available=true` вместе с `stale_owner=true` означает,
что процесс погиб, не обновив метаданные. Восстанавливайтесь только защищённой командой:

```powershell
.\scripts\hoh.ps1 lock-recover `
  --project-root C:\path\to\repo `
  --target execution `
  --json
```

Восстановление сначала захватывает ту же блокировку ядра с нулевым ожиданием. Оно не может сломать
живого владельца и никогда не удаляет файл блокировки. После прерванного прогона очереди изучите
журнал операций до изменения состояния очереди:

```powershell
.\scripts\hoh.ps1 reconcile-status --project-root C:\path\to\repo --json
```

Каждая нетерминальная операция классифицируется как `not_started`, `patch_applied`,
`commit_exists_state_missing`, `state_complete`, `contradictory` или `corrupted`. Старт очереди
автоматически завершает только точную идемпотентную запись состояния, когда совпадают трейлер
коммита, родитель, область изменённых файлов, чистота worktree, идентичность прогона или отката и
долговечная нагрузка проверки. Во время сверки он никогда не вызывает Worker и Critic.

Используйте `reconcile-apply` только с тем `safe_action`, который сообщил статус:

```powershell
.\scripts\hoh.ps1 reconcile-apply `
  --project-root C:\path\to\repo `
  --operation-id <идентификатор-операции> `
  --action complete-state `
  --json
```

`cancel-intent` принимается, только пока HEAD и worktree по-прежнему равны базовому состоянию.
`restore-patch` сначала доказывает точные ожидаемые хеши пост-образа и область, восстанавливает
только записанные базовые пути и проверяет базовое состояние. Журнал хранит SHA-256 патча и
пофайловые хеши базового состояния и пост-образа, а не сырой текст патча; вывод команд восстановления
проходит вырезание секретов. `finish-ledger` только закрывает операцию, чьи свидетельства в хранилище
состояния уже совпадают. Живая аренда исполнения, неожиданный HEAD, грязный путь, изменённое
содержимое, отсутствующий трейлер, повреждённый дайджест записи или противоречивое состояние блокируют
изменение.

Не используйте `queue-recover-running` и `/recover`, пока у задачи есть неразрешённые свидетельства
операции; обе команды отклоняют такой переход. Сначала разберитесь с журналом, затем при
необходимости восстановите действительно не начатую задачу.

Инъекция падения существует только для тестов. HoH распознаёт `HOH_TEST_CRASH_POINT`, только когда
`HOH_ENABLE_TEST_CRASH_INJECTION=1`; промышленные скрипты не должны задавать ни одну из этих
переменных.

Если команда отказала:

- изучите `rollback-history --json`
- убедитесь, что канонический `git status --porcelain` чист
- разберитесь с каждым сообщённым блокером, а не обходите его
- не используйте `reset --hard`

При успехе запишите коммит отката в отчёт об инциденте или изменении. Задача становится
`rolled_back`; финальная передача остаётся заблокированной, пока исправленный жизненный цикл того же
идентификатора задачи не дойдёт до `done`. Зависимые задачи в очереди остаются заблокированными
автоматически. Завершённые зависимые задачи нужно разрешить до того, как откат будет разрешён.

Как только бандл экспортирован, ожидающие или отклонённые свидетельства ревью делают
`supervisor-status` неготовым. Последний бандл рабочего элемента обязан иметь действительное
одобрение до передачи.

## Обязательный трёхголовый режим

Заказчик не настраивает роли в TOML. Во время брифинга Supervisor запускает:

```powershell
.\scripts\hoh.ps1 role-catalog --project-root C:\path\to\repo --refresh-registry --json
```

Спросите, какой агент должен быть Supervisor и Worker, нужен ли Critic, необязательные имена моделей и
предел попыток. Занесите ответы в project-spec v2 и запустите `project-plan --write --enqueue`. HoH
порождает `.hoh/role-profile.json`, и все команды исполнения загружают его автоматически. Один и тот
же продукт-агент может быть назначен на несколько ролей, но каждая роль получает отдельную личность
сессии.

Проверьте полный локальный автомат состояний до ежедневного использования:

```powershell
.\scripts\hoh.ps1 three-head-conformance --json
```

В обязательном режиме HoH всегда экспортирует точный бандл v2. При `[critic] driver = "manual"`
`queue-run-loop` останавливается на `review_pending`; доставьте канонический бандл настроенному
critic и импортируйте его решение v2:

```powershell
.\scripts\hoh.ps1 review-import --config .\harness.toml --decision .\critic-decision.json --json
```

При `[critic] driver = "claude_code"` очередь автоматически вызывает Claude Code с отключёнными
инструментами и сохранением сессии, импортирует схемно-ограниченное решение и продолжает после
одобрения. Если Claude недоступен, не аутентифицирован, вышел по таймауту или вернул некорректный
вывод, задача остаётся в `review_pending`. Повторяйте только ревью.

Любой другой ревьюирующий CLI только на чтение может использовать `[critic] driver = "command_json"`.
Он получает тот же неизменяемый промпт ревью на stdin и обязан вернуть на stdout только
документированный JSON решения; HoH добавляет хеши и аттестации и выполняет те же проверки импорта.

Любой закэшированный агент ACP Registry может вместо этого использовать `[critic] driver = "acp"`; HoH
запускает его вне репозитория, отклоняет все разрешения на инструменты, выбирает запрошенную модель
ACP, если она есть, и требует тот же JSON решения. Поэтому Critic на DeepSeek нуждается и в
идентификаторе harness (например, `qwen-code`), и в точном варианте модели DeepSeek, который этот
harness выставляет.

Для Critic только на модели настройте `[verifier_model]` и используйте
`[critic] driver = "model_json"` либо выберите `direct-critic-model` в GUI. Этот путь отправляет
структурированному провайдеру модели только неизменяемый review-бандл и не требует локального
исполняемого файла Critic:

```toml
[verifier_model]
provider = "deepseek"
model = "deepseek-chat"
api_key_env = "DEEPSEEK_API_KEY"

[critic]
driver = "model_json"
command = ""
```

Doctor падает до исполнения очереди, когда переменная с учётными данными или эндпоинт некорректны.
Отказы аутентификации, квоты или схемы у провайдера оставляют задачу в `review_pending`; повторяйте
через `critic-run`, не перезапуская Worker.

```powershell
.\scripts\hoh.ps1 critic-run --config .\harness.toml --project-root C:\path\to\repo --json
```

Эта команда переиспользует неизменяемый ожидающий бандл и не перезапускает Worker.

При `reject` изучите неизменяемые находки, затем дайте Supervisor'у подтвердить записанный brief:

```powershell
.\scripts\hoh.ps1 review-rework --config .\harness.toml --decision-id <идентификатор-решения> --json
.\scripts\hoh.ps1 queue-run-loop --config .\harness.toml --project-root C:\path\to\repo --json
```

`review-rework` не может заменить инструкции по исправлению или изменить исходную область задачи. Он
ставит в очередь следующую попытку, только если решение — последнее отклонение и предел попыток
бандла не достигнут. `escalate` и исчерпанные попытки остаются заблокированными и запускают
настроенный уведомитель Telegram. Токены и идентификаторы пользователя и чата остаются только в
переменных окружения.

Если заказчик отключает Critic, порождённый профиль использует `mode=disabled`: успешный кандидат
Worker'а становится `done` только после детерминированных проверок политики, приёмки и команд под
управлением Supervisor'а. Critic-бандл не создаётся. `three-head-conformance` проверяет и включённый,
и выключенный маршруты.

## Журнал взаимодействий

Изучите последние события с вырезанными секретами:

```powershell
.\scripts\hoh.ps1 journal-list --project-root C:\path\to\repo --limit 100
.\scripts\hoh.ps1 journal-list --project-root C:\path\to\repo --task-id task-001 --json

Выгрузите удобную для аудита стенограмму:

.\scripts\hoh.ps1 journal-export `

  --output C:\path\to\handoff\interaction-journal.md `
  --format markdown `

```

Журнал содержит маршрутизированные промпты и сообщения, доступную телеметрию инструментов ACP или
CLI, свидетельства возвращённого патча, проверочные команды и их вывод, действия Git, решения critic,
уведомления и переходы состояния. Вырезание секретов происходит до дописывания. Не ждите, что HoH
покажет приватные внутренние вызовы непрозрачного агента, который не раскрывает их через свой
протокол адаптера.

Когда сообщение или вызов инструмента Supervisor'а или Critic происходят во внешнем интерфейсе, этот
агент пишет закрытое событие по `schemas/journal-ingress-v1.schema.json` и дописывает его командой:

```powershell
.\scripts\hoh.ps1 journal-record `
  --project-root C:\path\to\repo `
  --event C:\path\to\journal-event.json `
  --json
```

Именно так разговор-брифинг становится частью той же ленты времени, хотя сам интерфейс провайдера
находится вне переносимого процесса HoH.

## Метрики использования, стоимости, длительности и качества

Изучите агрегированные свидетельства или неизменяемые лежащие в основе события:

```powershell
.\scripts\hoh.ps1 metrics-summary --project-root C:\path\to\repo --json
.\scripts\hoh.ps1 metrics-list --project-root C:\path\to\repo --limit 100 --json
```

HoH записывает сообщённые адаптером входные, выходные и суммарные токены, затраченное время агента,
сообщённую провайдером стоимость и объективные исходы завершения и ревью. Отсутствующая телеметрия
остаётся отсутствующей; HoH не выдумывает счётчики токенов и стоимость. Чтобы вычислить стоимость,
когда адаптер сообщает токены, но не сумму, добавьте точную ставку на десктопной странице **Метрики**
или настройте `metrics.prices` в `.hoh/harness.json`. Стоимость от провайдера всегда побеждает
вычисленную. Дописываемый файл событий — `usage-metrics.jsonl` под корнем состояния проекта, вне
канонического Git.

## Операции с провайдерами моделей

Держите API-ключи в переменных окружения процесса, а не в `harness.toml`:

```powershell
$env:OPENAI_API_KEY = "<секрет-сессии>"
$env:DEEPSEEK_API_KEY = "<секрет-сессии>"
.\scripts\hoh.ps1 doctor --config .\harness.toml
.\scripts\hoh.ps1 model-smoke --config .\harness.toml --role supervisor
```

Последняя команда работает только с конфигурацией. Чтобы разрешить один небольшой сетевой запрос,
добавьте `--live`. Порождайте план только после того, как изучите цель учётных данных и выбранную
модель:

```powershell
.\scripts\hoh.ps1 project-plan `
  --config .\harness.toml `
  --project-root C:\path\to\repo `
  --requirements C:\path\to\requirements.md `
  --write
```

Изучите порождённые бриф, дорожную карту и файлы задач до добавления `--enqueue`. События журнала от
провайдера содержат идентификаторы запросов, хеши, задержку, число попыток и счётчики токенов, но не
API-ключи и не тела промптов. Роли-заглушки сохраняют полностью офлайновое планирование через `--spec`
и проверку только детерминированными средствами.

## Передача по финальному аудиту

Настройте офлайновые языковые анализаторы в `harness.toml`:

```toml
[audit]
language_analyzers = ["python", "javascript", "typescript"]
entry_points = ["src/app.py", "src/index.ts"]
exclude_paths = ["vendor/**", "generated/**"]
fail_on_unavailable = true
```

Запустите отдельный аудит с той же политикой:

```powershell
.\scripts\hoh.ps1 audit --config .\harness.toml --check "python -m unittest discover -s tests" --markdown
```

Настроенные точки входа делают проверку достижимости строгой для языка, когда хотя бы один шаблон
совпадает с одним из его исходных файлов. Разберите каждую находку `*_UNUSED_FILE`, недостижимого
кода или неиспользуемого объявления и либо удалите и исправьте её сами, либо задокументируйте
намеренное исключение. HoH файлов не удаляет. Отсутствующий язык сообщается как `unsupported`;
отказавший исполнитель сообщается как `unavailable` и по умолчанию блокирует передачу.

Когда у проекта есть явные проверочные команды, передайте их значениями `-FinalCheck`:

```powershell
.\scripts\run-daily-ops.ps1 `
  -Config .\harness.toml `
  -FinalCheck "set PYTHONPATH=src&& python -m unittest discover -s tests" `
  -FinalCheck "python -m compileall -q src tests"
```

Когда очередь опустеет, HoH выполняет финальный аудит, сохраняет Markdown-свидетельства под корнем
состояния HoH и отправляет уведомление о готовности или о провале аудита в Telegram, если он включён.
Если какое-либо явно экспортированное последнее ревью ожидает или отклонено, передача останавливается
до аудита со статусом `status=review_blocked` и вместо этого отправляется уведомление о необходимости
действия пользователя.

## Операторские команды

- `/status` — счётчики очереди и число зависших задач.
- `/queue` — текущее состояние очереди.
- `/stale` — зависшие исполняющиеся задачи.
- `/retry <task-id>` — вернуть в очередь неудавшуюся задачу после разбора.
- `/recover <task-id> [причина]` — вернуть в очередь подтверждённую прерванную исполняющуюся задачу.
- `/continue` — подтвердить продолжение; чтобы возобновить работу, запустите `queue-run-loop`.
- `/stop` — записать решение об остановке, не меняя очередь.

Для снимка supervisor'а только на чтение, включающего счётчики очереди, идентификаторы зависших задач,
последний прогон, последний аудит, последнее операторское событие и гейты внешнего ревью:

```powershell
.\scripts\hoh.ps1 supervisor-status --project-root C:\path\to\repo
.\scripts\hoh.ps1 supervisor-status --project-root C:\path\to\repo --json
```
