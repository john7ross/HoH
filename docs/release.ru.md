# Промышленный релиз HoH

[English](release.md) · **Русский**

## Граница релиза

Канонический источник продукта — Git-репозиторий по пути `C:\path\to\repo`. Релизы для конечного
пользователя — нативные устанавливаемые приложения:

- Windows x64: `dist/HoH-Setup-<версия>.exe`, собирается `scripts/package-windows-installer.ps1`;
- Ubuntu/Debian: `dist/hoh_<версия>_<архитектура>.deb`, собирается `scripts/package-deb.sh` на Linux;
- macOS: `dist/HoH-<версия>.dmg`, собирается `scripts/package-macos.sh` на macOS.

Все три пакета несут собственные Python и Tk; пакет Debian объявляет только Git. Пользователи не
распаковывают архивы исходников и не вызывают Python. Операционное состояние, свидетельства ревью,
журналы операций, worktree попыток, конфигурация и учётные данные находятся вне установки приложения.

### Откуда какую платформу можно сопровождать

Запуск HoH поддерживается на всех трёх платформах. Выпуск и публикация релиза несимметричны, и этот
релиз не делает вид, что это не так:

| Задача | Windows | Linux | macOS |
|---|---|---|---|
| Запуск GUI, CLI и headless-сервера | да | да | да |
| Ежедневные операции (`scripts/run-daily-ops.*`) | да | да | да |
| Регистрация планировщика рабочего пространства | да | да (пользовательский таймер systemd) | да (LaunchAgent) |
| Сборка собственного пакета платформы | да | да | да |
| Сборка внутреннего payload'а обновления (`build-update-payload.ps1`) | да | нет | нет |
| Подпись каталога обновлений (`sign-catalog.ps1`) | да | нет | нет |
| Регистрация задания слежения за Telegram | да | нет | нет |

Поэтому канал обновлений и его подпись приходится готовить из Windows. Это ограничение
сопровождающего, а не пользователя: установленная сборка под Linux или macOS потребляет подписанный
каталог как обычно.

HoH не требует платного публичного сертификата подписи кода. Windows Setup не подписан, поэтому на
репутацию SmartScreen мы не претендуем. Сборка macOS использует ad-hoc подпись, поэтому Gatekeeper
может показать предупреждение о неопознанном разработчике, пока не появятся Developer ID и
нотаризация. Канал обновлений приложения независимо использует явно доверенную самоподписанную
RSA-личность издателя, подписанный статический JSON-каталог и точные размер и SHA-256 пакета.

HoH 1.0.0 даёт установку агентов и приложения в пользовательской области с проверкой целостности,
пошаговую вендорскую аутентификацию, три независимые роли, потоковую передачу и push A2A с OAuth и
OIDC, политику MCP по ролям, планирование нескольких проектов, метрики, доверенные обновления и работу
на десктопе и в headless-режиме. Он сохраняет поддержку обычного ACP Registry и декларативные
одноразовые профили Worker.

HoH ничего не утверждает о том, работает ли у вас конкретный агент. `compatibility-matrix` сообщает,
что установлено на этой машине:

```
python -m llm_harness compatibility-matrix --project-root . --json
```

Чтобы узнать, действительно ли роль запускается, запустите её: `role-conformance --role <роль>`
выполняет её один раз в одноразовом репозитории. Нативные установщики обязаны пройти смоук на
собственных операционных системах. Сопроводительный файл релиза авторитетен для точного исходного
коммита и хеша пакета.

`compatibility-matrix` описывает машину, на которой запущена, и больше ничего. После установки на
новую цель запустите там `role-conformance` для каждой роли, на которую собираетесь опираться.

Управляемые агенты живут в `%LOCALAPPDATA%\HoH\agents` и в приложение не вкладываются. Вендорские
сессии остаются в собственных хранилищах учётных данных вендоров. Метаданные подключения A2A для
проекта хранятся в `.hoh/harness.json`; значения bearer и API-key, а также клиентские секреты OAuth
живут только в окружении и в релиз не попадают. Токены device-flow для A2A хранятся отдельно в
`%LOCALAPPDATA%\HoH\oauth-tokens`, защищены DPAPI текущего пользователя Windows и никогда не
вкладываются в пакет.

## Сборка из чистого коммита

Windows:

```powershell
cd C:\path\to\repo
git status --short
$env:PYTHONPATH = (Resolve-Path .\src).Path
runtime\python\python.exe -m unittest discover -s tests
runtime\python\python.exe -m compileall -q src tests
.\scripts\hoh.ps1 driver-catalog --json
.\scripts\hoh.ps1 protocol-conformance --distribution-root . --json
.\scripts\hoh.ps1 three-head-conformance --json
.\scripts\package-windows-installer.ps1
```

Ubuntu/Debian и macOS обязаны собираться из того же чистого коммита на своих целевых системах:

```bash
bash scripts/bootstrap-runtime.sh  # только Linux: получить встроенный интерпретатор
bash scripts/package-deb.sh        # только Linux
bash scripts/package-macos.sh      # только macOS
```

Перед сборкой пакета `git status --short` обязан быть пуст. Каждый сборщик прогоняет модульный набор
тестов по исходникам, проверку компиляции и Doctor. Сборщик Windows дополнительно обновляет и
проверяет встроенный рантайм до компиляции Setup. Сборщику macOS нужен закреплённый PyInstaller на
релизном Mac; PyInstaller — зависимость сборки, конечным пользователям он не нужен.

Нативные сборщики запускают Doctor с изолированным временным кандидатом исполняемого файла
`release-smoke`, чтобы чистый сборщик мог проверить пакет, не требуя пользовательских CLI агентов.
Эта проба не записывается в конфигурацию приложения и не поставляется в пакете.

### Свидетельства кроссплатформенной сборки (2026-09-03)

Все три артефакта собраны из исходников, опубликованных как `v1.0.0`, и установлены на той
операционной системе, для которой предназначены. Ни один из них не собирался в CI. Здесь намеренно
назван тег, а не хеш коммита: история публикации каждый раз схлопывается в один коммит, поэтому
записанный тут хеш указывал бы в пустоту.

Они заменяют более раннюю загрузку v1.0.0, которую никто не успел скачать. Номер версии не
изменился, потому что в ней ничего не изменилось: пересборка несёт одно исправление в самом
продукте — headless-сервер на Windows садился на порт, который уже слушает другой процесс, вместо
отказа запускаться, — и отчёт аудита, который сообщает, почему команда проверки упала. Подмена
опубликованных файлов честна только вместе с заменой хешей здесь и в release notes и при условии,
что тег указывает на тот исходник, из которого они собраны.

| Артефакт | Байт | SHA-256 |
|---|---|---|
| `HoH-Setup-1.0.0.exe` | 17 887 456 | `2136e2aa446d9a1b807e78cf6a3767e3442b02a742cbbde32ba272f8af7ac762` |
| `hoh_1.0.0_amd64.deb` | 30 008 884 | `6e0275e086ebed1b3b3b74116f8537de2d1875fc83d2ca67e56fa6205ffb8c20` |
| `HoH-1.0.0.dmg` | 16 063 324 | `644a48d628674dc38acdc768d372f6ed449f4c82aca13b033bf679168d5f6591` |

Хеш считается после того, как артефакт создан, поэтому копия этой таблицы внутри самих артефактов
содержит значения предыдущего круга. Авторитетны файлы `.sha256`, публикуемые рядом с каждым
пакетом; таблица нужна, чтобы свидетельства и хеши лежали в одном месте.

Каждый установленный продукт проверялся одинаково: `doctor` вообще без конфигурации, из каталога,
который является репозиторием пользователя, а не чекаутом HoH; `doctor` на конфигурации UTF-8 с
меткой порядка байт; смоук GUI в обеих локалях и обеих темах; а также `protocol-conformance`,
`three-head-conformance` и `workflow-smoke`. Первая проверка появилась только сейчас: во всех
прежних кругах передавался stub-конфиг с `require_embedded_python = false`, то есть отключалась
ровно та проверка, которая падала у установленного пользователя Windows. Все вернули `ok: true`, смоук GUI прошёл 4 из 4 на
каждой платформе.

Windows 11, тихая установка для пользователя в `%LOCALAPPDATA%\Programs\HoH`: встроенные CPython
3.11.15 и Tk 8.6; вне интерпретатора нет скомпилированного байткода; `THIRD-PARTY-NOTICES` и все 18
русских документов на месте. Деинсталлятор не оставил ни каталога установки, ни папки в меню
«Пуск», ни ключа в реестре удаления программ.

Пакет Debian вырос на пять мегабайт: стандартная библиотека интерпретатора теперь компилируется во
время сборки с записью установочного пути, а не едет такой, какой её оставило сборочное дерево.
`/opt` принадлежит root, кэшировать байткод туда пользователь не может; без готового байткода каждый
запуск перекомпилировал бы стандартную библиотеку и выбрасывал результат.

Ubuntu 26.04, `dpkg -i`: встроенные CPython 3.11.16 и Tk 9.0, поэтому единственная зависимость —
`git`; ничего доступного на запись всем; нет байткода со сборочной машины и нет файла, называющего
её путь; `LICENSE`, `NOTICE`, `THIRD-PARTY-NOTICES`, `/usr/share/doc/hoh/copyright` и все 18
русских документов на месте. Файл `.sha256` содержит только имя файла, поэтому `sha256sum -c`
проходит из каталога пакета на любой машине.

macOS, DMG смонтирован и приложение скопировано в `/Applications`: подпись проверяется командой
`codesign --verify --deep --strict`, `THIRD-PARTY-NOTICES` и все 18 русских документов лежат внутри
бандла.

Эти проверки выявили три дефекта, исправленных в перечисленных выше артефактах: пакеты не несли
уведомления о сторонних лицензиях; сценарии сборки не запускались в том PowerShell, который
поставляется с Windows; внутри бандла macOS любая операция GUI открывала вторую копию приложения
вместо запуска команды.

### Более ранние кроссплатформенные свидетельства (2026-08-29, устарели)

Те нативные артефакты собирались из актуального на тот момент коммита и проходили смоук на каждой
цели. Они предшествуют работе над релизом 1.0.0 и записаны только как история:

- Windows x64: точная попытка Codex ACP с gpt-5.4 дошла до провайдера, но была отклонена лимитом
  использования Codex.
- Ubuntu 26.04 x86_64: тогдашний DEB установился успешно; упакованные `doctor` и `hoh-gui --smoke`
  прошли. После установки Node.js 22.14 в пользовательскую область Supervisor, Worker и Critic все
  дошли до адаптера ACP, но вернули `Authentication required`.
- macOS 15.1 x86_64: тогдашний DMG прошёл на целевой стороне проверку ad-hoc подписи, CLI, лицензии и
  уведомления, а также смоук GUI. После установки Node.js 22.14 в пользовательскую область все три
  роли Codex ACP вернули `Authentication required`.

Запустившийся пакет — это не работающая учётная запись у вендора. Ни один из этих результатов ничего
не говорит о том, работает ли у вас Codex на Ubuntu или macOS; об этом говорит только прогон
`role-conformance` на вашей машине.

## Публикация релиза

Релизы публикуются вручную, из пакетов, собранных и установленных на той операционной системе, для
которой каждый предназначен. В этом и смысл: опубликованы те самые байты, которые действительно
поставили и запустили, а не те, что собрал раннер и никто не открывал.

Автоматически не публикуется ничего. `.github/workflows/release.yml` собирает три пакета на чистых
раннерах и оставляет их артефактами своего запуска, и стартует только по вашей команде:
**Actions → Build native packages → Run workflow**. Он нужен, чтобы убедиться, что сценарии упаковки
всё ещё работают на машине, которая не ваша; брать его артефакты как релиз не нужно.

Раньше он запускался по тегу `v*` и сам создавал релиз. При ручной публикации это означало три
сборки на раннерах для уже существующего релиза, а проверка, которая не давала ему ничего
перезаписать, срабатывала только после того, как эти сборки заканчивались.

## Ручная загрузка релиза на GitHub

Интерфейс GitHub позволяет опубликовать релиз, не используя шаг `gh release create` из workflow.
Держите исходный тег и каждый нативный пакет на одном и том же чистом коммите:

1. Отправьте `main`, создайте тег релиза (например, `v1.0.0`) и переключитесь ровно на этот тег на
   каждой сборочной машине.
2. **Удалите `dist/` и `build/` до сборки.** Оба игнорируются Git, поэтому рабочее дерево может
   содержать артефакты любого прежнего коммита, и на шаге загрузки этого никто не заметит.
3. Соберите Windows Setup, DEB для Ubuntu/Debian и DMG для macOS из этого тега. Не смешивайте старый
   локальный артефакт из `dist/` или `build/` с более новым тегом исходников; манифест Windows
   записывает точный исходный коммит, а сопроводительные `.sha256` называют только файл, но не его
   путь.
4. В **GitHub → Releases → Draft a new release** выберите тег, задайте заголовок и вставьте
   [`RELEASE_NOTES.ru.md`](../RELEASE_NOTES.ru.md) или [`RELEASE_NOTES.md`](../RELEASE_NOTES.md).
5. Загрузите эти файлы (два файла `.sha256` и манифест Windows — часть свидетельств релиза):

   - `HoH-Setup-<версия>.exe`
   - `HoH-Setup-<версия>.manifest.json`
   - `hoh_<версия>_amd64.deb`
   - `hoh_<версия>_amd64.deb.sha256`
   - `HoH-<версия>.dmg`
   - `HoH-<версия>.dmg.sha256`

6. Оставьте включённым **Set as the latest release**, проверьте имена ресурсов и заметки, затем
   публикуйте.

Сборочный workflow репозитория выполняет те же три сборки на чистых раннерах, но только когда вы
запускаете его сами: **Actions → Build native packages → Run workflow**, и ничего не публикует.
Он нужен, чтобы убедиться, что сценарии упаковки работают на машине, которая не ваша; в релизе
остаются пакеты, которые вы установили и проверили лично.

## Проверка с холодного старта

Установите в чистый целевой профиль. Не копируйте в него локальную конфигурацию, операционное
состояние, вендорские учётные данные и закэшированные пути Python.

```powershell
.\dist\HoH-Setup-1.0.0.exe /VERYSILENT /NORESTART
& "$env:LOCALAPPDATA\Programs\HoH\launch-hoh.ps1" doctor
& "$env:LOCALAPPDATA\Programs\HoH\launch-hoh.ps1" gui --smoke --locale ru --theme dark
```

```bash
sudo apt install ./dist/hoh_1.0.0_amd64.deb
hoh doctor
hoh-gui --smoke --locale ru --theme dark
```

На macOS установите `HoH.app` из DMG в `/Applications`, запустите из Finder, затем выполните
`/Applications/HoH.app/Contents/MacOS/HoH doctor` для свидетельств CLI. Поскольку пакет подписан
ad-hoc, Gatekeeper блокирует первый запуск. На macOS 15 и новее откройте **Системные настройки →
Конфиденциальность и безопасность** и нажмите **Открыть всё равно** под сообщением с именем HoH:
в macOS 15 обход через Control-клик → **Открыть** убрали, поэтому старая инструкция оставляет
пользователя в тупике. На более ранних macOS Finder → правая кнопка на `HoH.app` → **Открыть**
по-прежнему работает. Для локальной сборки это ожидаемо и не является заявкой на Developer ID и
нотаризацию. Записывайте точную ОС, архитектуру, хеш пакета, результаты
смоука GUI, удаления и переустановки и мастера первого запуска отдельно для каждой цели. Результат на
Windows или Linux ничего не говорит о macOS.

Перед публичным распространением прогоните также живой `worker-conformance` для каждого вложенного
драйвера провайдера, объявленного в этом релизе работоспособным. Детерминированная регрессия
неизвестного агента доказывает границу обычного `command`, но не доказывает учётные данные и поведение
внешнего CLI провайдера.

## Самоподписанный издатель и бесплатный статический канал

Создайте издателя один раз. PFX приватен и защищён паролем; пользователям распространяется только
публичный JSON:

```powershell
.\scripts\new-self-signed-publisher.ps1 -OutputDir "$env:LOCALAPPDATA\HoH\publisher"
.\scripts\hoh.ps1 publisher import --publisher "$env:LOCALAPPDATA\HoH\publisher\hoh-publisher.public.json"
```

Соберите payload релиза с его окончательным URL загрузки по HTTPS и подпишите его. Достаточно
статического хостинга вроде GitHub Pages; платный сервис каталога не нужен:

```powershell
.\scripts\build-update-payload.ps1 `
  -ReleaseUrl "https://downloads.example/HoH-update-payload.zip" `
  -PublisherPfx "$env:LOCALAPPDATA\HoH\publisher\hoh-publisher.pfx"
```

Десктопная страница **Настройки проекта** импортирует публичный JSON издателя, проверяет подписанный
канал и устанавливает проверенное обновление рядом с работающей версией. Эквивалентные команды:

```powershell
.\scripts\hoh.ps1 update check --source https://downloads.example/HoH-releases.signed.json
.\scripts\hoh.ps1 update install --source https://downloads.example/HoH-releases.signed.json
.\scripts\hoh.ps1 update status
.\scripts\hoh.ps1 update rollback
```

Неподписанные, недоверенные, подменённые пакеты, пакеты не для той платформы, неверного размера,
неверного хеша, не по HTTPS, с выходом за пределы архива и с символическими ссылками приводят к отказу
закрытым. Установки живут в `%LOCALAPPDATA%\Programs\HoH\versions`; `current.json` меняется только
после успешной распаковки.

Тот же формат подписанного конверта несёт централизованные факты о совместимости. Опубликуйте
подписанный payload на основе `catalogs/compatibility.payload.example.json`, затем изучайте его
отдельно от локальных живых свидетельств:

```powershell
.\scripts\hoh.ps1 compatibility-matrix --project-root . `
  --central-catalog https://downloads.example/HoH-compatibility.signed.json --json
```

Централизованный каталог описывает то, что наблюдал кто-то другой. Об этой машине говорит только
`role-conformance` на этой машине.

## Обновление

1. Остановите циклы очереди и запланированный опрос Telegram для заменяемой установки.
2. Запишите `lock-status`, `reconcile-status`, `supervisor-status` и текущий манифест релиза.
3. Сделайте резервную копию корней `.hoh-state/<хеш-репозитория>` и `.hoh-leases/<хеш-репозитория>`
   вместе. Сохраните ожидающие review-бандлы и записи операций.
4. Проверьте хеш нативного установщика или используйте доверенный подписанный каталог релизов для
   обновления внутри приложения.
5. Установите новые Setup, DEB или DMG через процесс пакетов операционной системы.
6. Сохраните принадлежащую оператору конфигурацию проекта и настройку окружения; не копируйте старые
   каталоги пакетов рантайма.
7. Прогоните doctor и сверку только на чтение против каждого управляемого репозитория до
   возобновления работы.
8. Держите прежний установщик, манифест, резервную копию конфигурации и состояния, пока новый релиз не
   отработает представительный цикл очереди.

## Резервное копирование и восстановление

Состояние и свидетельства журнала — одна единица восстановления:

- `.hoh-state/<хеш-репозитория>` содержит очередь, историю, журнал, ревью, решения, аудиты, откаты,
  смещения Telegram и операторские события;
- `.hoh-leases/<хеш-репозитория>/operations` содержит записи сверки после падения;
- канонический Git-репозиторий содержит коммиты и точную историю файлов, на которую ссылаются
  свидетельства.

Восстанавливайте все три из взаимно согласованной точки. После восстановления запустите
`lock-status`, `reconcile-status`, `supervisor-status` и `doctor` до любой изменяющей команды.
Никогда не выбрасывайте ожидающую запись операции только ради разблокировки очереди.

## Хранение свидетельств

Храните манифесты релизов и хеши установщиков для каждой переданной сборки. Храните свидетельства
неудавшихся прогонов, когда они нужны, чтобы объяснить промышленный инцидент, решение о безопасности
или ограничение живого провайдера. Детерминированное соответствие на заглушках доказывает поведение
автомата состояний, но не доказывает живого провайдера. Точно так же успешный коммит Worker'а с
ожидающим ревью Critic не является завершённым трёхголовым прогоном.

Решения «сохранить, заархивировать, удалить» для рабочего пространства записаны в
`docs/workspace-cleanup.ru.md`.
