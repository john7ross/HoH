# Встроенный рантайм

[English](runtime.md) · **Русский**

## Требование

Промышленные прогоны не должны зависеть от системного Python пользователя. Harness обязан
поставляться или устанавливаться со встроенным рантаймом Python и вложенными зависимостями.

## Раскладка

```text
runtime/
  python/
    python.exe
  site-packages/
vendor/
  wheels/
schemas/
  protocol-envelope-v1.schema.json
  review-bundle-v1.schema.json
  verifier-decision-v1.schema.json
  critic-review-bundle-v2.schema.json
  critic-decision-v2.schema.json
  project-spec-v2.schema.json
  role-profile-v1.schema.json
  role-profile-v2.schema.json
  driver-manifest-v1.schema.json
  journal-event-v1.schema.json
  journal-ingress-v1.schema.json
examples/
  protocol/
```

Ожидаемый путь интерпретатора на Windows — `runtime/python/python.exe`.

## Политика зависимостей

- Зависимости рантайма закреплены в отслеживаемом файле `requirements.lock`.
- Закреплённые зависимости хранятся как колёса в `vendor/wheels`.
- Установка обязана использовать `--no-index --find-links vendor/wheels`.
- Ни одна зависимость рантайма не должна разрешаться из интернета при обычном исполнении.
- Системный Python допустим для разработки, тестов сборки и модели зависимостей пакета Debian;
  пользователи приложений на Windows и macOS получают вложенный рантайм.
- У текущего рантайма нет сторонних пакетных зависимостей; `requirements.lock` фиксирует это решение
  явно и обязан обновляться до добавления рантайм-зависимостей в `pyproject.toml`.

## Проверка

Используйте:

```powershell
python -m llm_harness runtime
```

Проверка требует:

- настроенный встроенный `python.exe` существует
- настроенный встроенный `python.exe --version` успешно запускается
- `vendor/wheels` существует
- `vendor/wheels` содержит хотя бы один файл `.whl`

Проверка рантайма проходит после того, как `scripts/bootstrap-runtime.ps1` скопировал подготовленный
рантайм Python, а `scripts/build-wheelhouse.ps1` или `scripts/build-update-payload.ps1` наполнил
`vendor/wheels`.

## Начальная подготовка

Используйте подготовленный каталог Python как источник:

```powershell
.\scripts\bootstrap-runtime.ps1 -PythonSource "C:\path\to\python" -BuildWheelhouse
```

Каталог-источник обязан содержать `python.exe`. Скрипт копирует этот рантайм в `runtime/python`,
создаёт `vendor/wheels`, проверяет, что встроенный интерпретатор запускается, и по желанию собирает
wheelhouse.

Полная локальная подготовка из подготовленного каталога Python:

```powershell
.\scripts\bootstrap-runtime.ps1 `
  -PythonSource "C:\path\to\python" `
  -BuildWheelhouse `
  -InstallOffline
```

Чтобы собрать или обновить только wheelhouse:

```powershell
.\scripts\build-wheelhouse.ps1
```

Обычная упакованная установка обязана ставить только из wheelhouse:

```powershell
.\runtime\python\python.exe -m pip install --no-index --find-links .\vendor\wheels llm-harness
```

Поставляемый офлайновый установщик следует этой политике и устанавливает в `runtime/site-packages`:

```powershell
.\scripts\install-offline.ps1
```

Во время разработки из исходников запускайте HoH через лаунчер репозитория:

```powershell
.\scripts\hoh.ps1 init-project
.\scripts\hoh.ps1 doctor
.\scripts\hoh.ps1 scan
```

## Нативные пакеты приложения

После подготовки рантайма и офлайновой установки соберите установщик Windows:

```powershell
.\scripts\package-windows-installer.ps1
```

Сборщик отказывается создавать Setup, если не выполнено следующее:

- `runtime/python/python.exe` существует
- `runtime/site-packages` существует
- `vendor/wheels` содержит файлы `.whl`
- `scripts/hoh.ps1` существует
- `doctor` проходит, включая предполётную проверку настроенного исполняемого файла worker'а
- `audit` проходит с `doctor` в качестве проверочной команды

Сборщик Windows сначала пересобирает wheelhouse из текущего дерева исходников и обновляет
`runtime/site-packages` через `scripts/install-offline.ps1`. Это не даёт упаковать устаревший
установленный код после изменений в исходниках. Сборщик внутреннего payload'а сохраняет
`-SkipRefresh` только для локальной диагностики.

Сборщик пишет `dist/HoH-Setup-<версия>.manifest.json`. Этот сопроводительный файл связывает SHA-256 и
размер Setup с точным чистым коммитом исходников. У внутреннего payload'а обновления собственный
подробный манифест рантайма, lock'а зависимостей, колёс, Doctor и аудита.

Держите Setup и его манифест вместе. Проверить их можно, не импортируя HoH:

```powershell
$manifest = Get-Content .\dist\HoH-Setup-1.0.0.manifest.json -Raw | ConvertFrom-Json
$actual = (Get-FileHash .\dist\HoH-Setup-1.0.0.exe -Algorithm SHA256).Hash.ToLowerInvariant()
if ($actual -ne $manifest.package.sha256) { throw "Setup digest mismatch" }
```

Windows x64 использует встроенный рантайм и `package-windows-installer.ps1`. Ubuntu и Debian
используют `package-deb.sh`; интерпретатор входит внутрь пакета, из зависимостей объявлен только Git.
macOS использует `package-macos.sh`; PyInstaller вкладывает Python и Tk в `HoH.app`, а `hdiutil`
создаёт DMG. Внутри бандла `sys.executable` — само приложение, поэтому оно читает `-m` и `-c` так же,
как интерпретатор: GUI запускает каждую операцию как `-m llm_harness <подкоманда>`, и без этого
кнопки открывали вторую копию приложения. По той же причине allow-list команд проверки принимает ту
программу, которой HoH запущен сам: `python3` в исходном чекауте и приложение внутри бандла. Все сборщики прогоняют тесты, компиляцию и Doctor из чистого чекаута. Сборка на одной ОС
не удостоверяет другую; каждому установщику нужны установка на целевой машине и смоук GUI,
headless-режима, обновления и удаления.

Нативные пакеты включают приложение, обязательные схемы, безопасные примеры, помощники планировщика и
шаблон конфигурации. Сырые токены Telegram в примере конфигурации не хранятся.

Доступ к моделям OpenAI и DeepSeek тоже использует только HTTPS-клиент стандартной библиотеки Python,
поэтому рантайм не добавляет колёс с SDK провайдеров. Учётные данные читаются в момент вызова из
`OPENAI_API_KEY` и `DEEPSEEK_API_KEY` либо из явно настроенного `api_key_env`. `doctor` проверяет
конфигурацию и наличие переменных окружения без доступа к сети. `model-smoke` остаётся офлайновым,
пока оператор не добавит `--live`.

Интеграции worker'ов Claude Code и OpenClaw не добавляют пакетов Python. Они вызывают установленные
оператором исполняемые файлы CLI через границу процессов стандартной библиотеки. `worker-smoke` по
умолчанию выполняет локальную пробу `--version`; ход с участием модели начинает только `--live`.
Приложение не несёт внутри ни один из этих внешних CLI, их учётные данные и их постоянное состояние.

Обычным CLI-worker'ам не нужны дополнительные зависимости Python внутри HoH. Настройте
`[worker] driver = "command"` с исполняемым файлом worker'а и аргументами; HoH запускает его из
изолированного worktree попытки, передаёт данные задачи через stdin и переменные окружения `HOH_*`, а
затем собирает diff.

CLI, которым нужен флаг файла промпта или обязательные неинтерактивные аргументы и аргументы
безопасности, используют `[worker] driver = "process"` вместе с `worker.process_profile` либо выбор
агента из каталога, чей `worker_process_profile` объявляет этот контракт. Aider присутствует в
каталоге по умолчанию с файловым профилем промпта и принудительными аргументами `--no-auto-commits` и
`--no-dirty-commits`. Он остаётся внешним исполняемым файлом, установленным оператором, и берёт ключи
провайдера из окружения процесса.

Менеджер попыток проверяет, что `HEAD` в Git не сдвинулся, до сбора любого diff Worker'а. Это не
зависит от выбранного адаптера: CLI, который коммитит вопреки объявленным флагам, приводит к отказу
закрытым, а его одноразовая попытка удаляется без изменения канонической истории.

Прежде чем использовать живого worker'а в ежедневной работе, запустите набор проверок соответствия
адаптера из переносимого лаунчера:

```powershell
.\scripts\hoh.ps1 worker-conformance --config .\harness.toml --timeout 300
```

Набор создаёт одноразовый git-репозиторий, прогоняет настроенного worker'а тем же путём supervisor'а и
верификатора, что и `worker-run`, проверяет манифест возможностей worker'а, проверяет созданный
worker'ом артефакт, коммитит через supervisor'а и подтверждает, что канонический worktree чист.
Используйте `--keep`, только когда путь к временному репозиторию нужен для отладки.

Для Hermes сначала выполните более дешёвую проверку доступности ACP:

```powershell
.\scripts\hoh.ps1 hermes-check
.\scripts\hoh.ps1 worker-conformance --config .\harness.toml --timeout 300
```

На нативной Windows HoH запускает дочерний процесс ACP с `CREATE_BREAKAWAY_FROM_JOB`, потому что
Hermes v0.20.0 иначе может войти во взаимную блокировку, пробуя Git Bash из вложенного задания
десктопного процесса. Ограниченный дочерний bootstrap короткозамыкает только точную апстримную команду
пробы работоспособности; обычные команды и запросы разрешений ACP не меняются. HoH также задаёт
`HERMES_ACP_SKIP_CONFIGURED_MCP=1`; Worker'у доступны только те MCP-серверы, которые явно переданы
изолированной ACP-сессией.

Чтобы проверить весь ежедневный процесс, обращённый к supervisor'у, без внешних секретов:

```powershell
.\scripts\hoh.ps1 workflow-smoke
.\scripts\hoh.ps1 workflow-smoke --mode blocker
```

Первая команда доказывает одноразовый путь готовности от спецификации проекта до передачи по
финальному аудиту. Вторая доказывает путь блокера и контракт уведомления-заглушки.

Чтобы проверить границу внешнего supervisor'а и верификатора из исходников или свежераспакованного
пакета:

```powershell
.\scripts\hoh.ps1 protocol-conformance --distribution-root . --json
```

Эта команда проверяет вложенные JSON-ресурсы и прогоняет офлайновый одноразовый поток через коммит,
принадлежащий supervisor'у, экспорт review-бандла, ожидающий гейт, импорт внешнего одобрения, гейт
готовности и проверку чистоты канонического git. Она не использует API провайдеров, доступ к сети и
секреты.

Чтобы проверить строгий трёхролевой автомат состояний из исходников или свежераспакованного пакета:

```powershell
.\scripts\hoh.ps1 three-head-conformance --json
```

Этот офлайновый смоук покрывает одобрение critic, отклонение с неизменяемым correction brief, вторую
попытку с подтверждением Supervisor'а, финальное одобрение, эскалацию, закрытие при выключенном Critic
и чистое каноническое состояние git.

Выбор рантайма проекта порождается, а не правится руками. `project-plan --write` читает выбор ролей из
project-spec v2 и создаёт `.hoh/role-profile.json`. Переносимый лаунчер автоматически объединяет этот
профиль с каталогом установленных агентов для `doctor`, исполнения worker'а и очереди и команд ревью.
Заказчик только отвечает на вопросы брифинга.

Стенограмма взаимодействий хранится как JSONL с вырезанными секретами под внешним корнем состояния
HoH, а не в переносимом ZIP приложения и не в канонической истории проекта. Выгружайте её явно
командой `journal-export`, когда заказчику или аудитору нужна копия в Markdown или JSONL.

Записи операций репозитория живут рядом с арендой исполнения по пути
`<репозиторий-родитель>/.hoh-leases/<имя-репозитория>-<хеш>/operations/<идентификатор-операции>.json`.
Они намеренно вынесены и из канонического репозитория, и из переносимого ZIP. Каждая атомарная
перезапись несёт дайджест записи SHA-256; некорректные или изменённые записи приводят к отказу
закрытым. Копируйте этот каталог вместе с соответствующим корнем состояния, когда сохраняете
свидетельства инцидента. Записи содержат дайджесты патча и состояния файлов, а не сырой текст патча, а
текст нагрузки восстановления проходит вырезание секретов до долговечной записи.

## Задание опроса Telegram на Windows

Для ежедневной операторской связи на Windows зарегистрируйте ограниченное запланированное задание
вокруг переносимого лаунчера:

```powershell
.\scripts\register-telegram-watch-task.ps1 `
  -Config .\harness.toml `
  -EveryMinutes 1 `
  -Iterations 1 `
  -RunNow
```

Задание запускает `scripts\hoh.ps1 telegram-watch` через встроенный рантайм. Запуски по расписанию
требуют, чтобы `-Iterations` было не меньше `1`, иначе повторяющееся расписание запускало бы
неограниченные долгоживущие процессы. Для непрерывного опроса используйте ручную сессию:

```powershell
.\scripts\hoh.ps1 telegram-watch --config .\harness.toml --iterations 0
```

Удалите запланированное задание так:

```powershell
.\scripts\register-telegram-watch-task.ps1 -Unregister
```

Токены и идентификаторы Telegram остаются вне файлов проекта. Задание выполняется в контексте текущего
интерактивного пользователя и читает переменные окружения, названные в `harness.toml`.

## Обёртка ежедневных операций

Используйте `scripts/run-daily-ops.ps1`, чтобы запускать промышленный цикл очереди через переносимый
лаунчер:

```powershell
.\scripts\run-daily-ops.ps1 `
  -Config .\harness.toml `
  -TimeoutSeconds 300 `
  -StaleMinutes 60
```

Обёртка сначала запускает `doctor` и останавливается до исполнения worker'а, если окружение не готово.
Когда переданы значения `-FinalCheck`, обёртка включает `queue-run-loop --final-audit` и передаёт
каждую проверку в гейт аудита. Полный операторский рунбук — в `docs/daily-ops.ru.md`.

Только для разработки лаунчер может использовать `src/`, когда офлайновой установки не было:

```powershell
.\scripts\hoh.ps1 -Python python -AllowSourceFallback doctor
```
